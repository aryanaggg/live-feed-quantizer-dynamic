LIVE FEED QUANTIZER - UI/STRUCTURAL AUDIT REPORT

=============================================================
1. EXECUTIVE SUMMARY
=============================================================
The application is a full-stack web app for real-time camera feed
quantization with audio-driven color palettes. It uses FastAPI/UVicorn
for the backend WebSocket server and vanilla JS/WebGL for the frontend.

Overall status: FUNCTIONAL but has several structural, visual and
functional issues that should be addressed.

=============================================================
2. STRUCTURAL ISSUES
=============================================================

2.1 MISLEADING COMMENT (index.html line 694)
  Severity: LOW
  Location: Line 694: `// <-- added closing for forEach`
  Description: The forEach callback on line 691 has its own { } block,
  so the comment "added closing for forEach" is misleading. It suggests
  a fix was applied but the comment is unnecessary and confusing.
  Code maintainability issue.
  Recommendation: Remove the misleading comment.

2.2 WEBGL ERROR REPLACES ENTIRE PAGE (index.html lines 279-282)
  Severity: MEDIUM
  Location: Lines 279-282
  Description: When WebGL is unavailable, the code replaces the entire
  document.body.innerHTML with an error message, completely removing
  all UI elements, event listeners, and application state. This is a
  "nuclear option" that provides poor user experience.
  Recommendation: Show the error in a modal or overlay rather than
  replacing the entire page content. Preserve the UI and explain the
  WebGL issue.

2.3 LOCALSTORAGE DEPENDENCY THROUGHOUT
  Severity: MEDIUM
  Location: Throughout index.html
  Description: The application relies heavily on localStorage for state
  persistence (audio quality settings, selected feeds/mics, gains).
  If localStorage is cleared, corrupted, or unavailable (e.g., private
  browsing mode), the app reverts to defaults but may behave
  unexpectedly. No migration or fallback logic exists.
  Recommendation: Add try/catch around all localStorage access with
  graceful defaults, and consider adding a "reset settings" option.

2.4 wsUrl() FUNCTION EDGE CASES (index.html lines 423-427)
  Severity: MEDIUM
  Location: Lines 423-427
  Description: The WebSocket URL construction function has potential
  issues:
  - If `backend` query param is used with a URL that has different
    protocol than location.protocol, the WebSocket protocol might be
    incorrect
  - The default protocol detection uses `location.protocol === 'https:'`
    which might not match if the page is served through a proxy
  - No validation of the constructed URL before connecting
  Recommendation: Add URL validation and test with various query param
  configurations.

2.5 REDUNDANT CODE IN AUDIO QUALITY CHIPS (index.html lines 691-694)
  Severity: LOW
  Location: Lines 691-694
  Description: The forEach closing comment `// <-- added closing for
  forEach` suggests the code was recently modified. The code itself is
  correct, but the comment should be cleaned up.
  Recommendation: Remove the misleading comment, ensure proper code
  review process to prevent such comments.

=============================================================
3. VISUAL BUGS & STYLING ISSUES
=============================================================

3.1 PULSE ANIMATION MAY NOT FULLY RESPECT REDUCED MOTION
  Severity: MEDIUM
  Location: CSS :root pulse animation and @keyframes pulse
  Description: The #hint element has `animation:pulse 3.4s ease-in-out
  infinite` (line 19). The `prefers-reduced-motion:reduce` media
  query on line 130 does `*{animation:none!important;transition-duration:.01ms!important}`
  which should disable it, but:
  - The pulse keyframes are still parsed by the browser
  - There could be a FOUC (Flash of Unstyled Content) before the
    media query takes effect
  - Not all browsers may respect the media query correctly
  Recommendation: Either remove the pulse animation entirely or
  ensure it's strictly gated by the media query at the HTML level.

3.2 MIX-BLEND-MODE:SCREEN COULD CAUSE UNEXPECTED VISUALS
  Severity: LOW
  Location: CSS: `body.ov #grid{z-index:2;mix-blend-mode:screen;pointer-events:none}`
  Description: The `mix-blend-mode:screen` on the grid overlay will
  brighten dark areas and can cause color shifts depending on the
  video content. This might make the quantized video look washed out
  or distorted on certain feeds.
  Recommendation: Test with various video content and consider
  limiting the blend mode or providing a user toggle with a warning.

3.3 GRID VIRTUAL CURSOR ON TOUCH DEVICES
  Severity: LOW
  Location: JavaScript: `addEventListener('pointermove', ...)`
  Description: The grid drawing code tracks pointer position with
  `lastMove` timestamp. If no pointer move occurs for 2.5 seconds,
  a "virtual cursor" wanders automatically. On touch-only devices
  without pointer events, `lastMay` may never update from a genuine
  user gesture, causing the virtual cursor to always be "stale".
  Recommendation: Also listen for `touchmove` events or add a
  touch-detection check.

3.4 DOCK --LVL VARIABLE EXTREMES
  Severity: LOW
  Location: CSS variable `--lvl` set in render loop (line 398)
  Description: The dock's box-shadow color depends on `--lvl` which is
  set to `((band[0] + band[1] + band[2]) / 3).toFixed(3)`. If audio
  is silent (all bands = 0), the dock becomes almost invisible
  (`--lvl: 0.000`). This might look broken if the video starts before
  audio input is active.
  Recommendation: Add a minimum value floor or use a different
  visual indicator for the silent state.

=============================================================
4. FUNCTIONAL BUGS
=============================================================

4.1 RENDER LOOP FRAME SKIP CONDITION (index.html lines 382-383)
  Severity: HIGH
  Location: Lines 382-383 in the `frame()` function:
  `const f0 = curFeed(), m = f0 && f0.open ? (f0.kind === 'local' ? (f0.v.readyState >= 2 && f0.v.videoWidth ? f0.v : null) : f0.bmp) : null;
  if (!m) return;`
  Description: If the local video element's `readyState` is < 2 or
  `videoWidth` is 0, the frame is skipped entirely. This means if the
  camera track takes time to become ready after `play()`, the quantizer
  will stop processing frames until the next valid frame arrives.
  The condition `f0.v.readyState >= 2` requires `HAVE_CURRENT_DATA`
  or higher, which might not be immediate after `play()`.
  Recommendation: Lower the readyState threshold or add a loading
  state, and ensure the render loop recovers when the video becomes ready.

4.2 AUDIO CONTEXT RESUME TIMING (index.html lines 500-506)
  Severity: HIGH
  Location: `ensureAC()` function
  Description: The Web Audio API requires a user gesture to resume the
  context from 'suspended' state. The `ensureAC()` function assumes
  that if `ac.state !== 'closed'`, it can be resumed. However, if the
  page was loaded without an initial user gesture (e.g., via programmatic
  launch), the audio context might remain suspended and no audio will
  be processed.
  Recommendation: Require an explicit user gesture (e.g., first click)
  to initialize audio, or add a visual indication that audio is
  unavailable until user interaction.

4.3 CAMERA SOURCE SWITCHING RACE CONDITION (server.py lines 700-752)
  Severity: MEDIUM
  Location: WebSocket handler `_WebSocketSession.camera_source` switching
  Description: When switching camera sources (lines 700-752), the code
  stops existing loops and starts new ones. There might be a race
  condition where:
  - The old IP camera loop hasn't fully stopped
  - The new RTSP/ONVIF loop tries to use the same resources
  - `session.reset_camera_locks()` might not fully clean up
  Recommendation: Add proper synchronization with `asyncio.Event`
  signals and ensure old tasks are fully cancelled before starting
  new ones.

4.4 wsUrl() PROTOCOL MISMATCH
  Severity: MEDIUM
  Location: `wsUrl()` function (index.html lines 423-427)
  Description: The function constructs WebSocket URLs based on the
  `backend` query param or `location.protocol`. If the page is loaded
  on `http://localhost` but the backend is on a different port or host,
  the WebSocket might connect to an incorrect URL. The default case
  uses `location.protocol === 'https:'` to determine `wss://` vs
  `ws://`, which might not match the actual server protocol.
  Recommendation: Add explicit protocol configuration or validate
  the WebSocket connection on open.

4.5 START() FUNCTION INCONSISTENT STATE (index.html lines 568-577)
  Severity: MEDIUM
  Location: `start()` function
  Description: If `refreshDevices()` runs but no camera is found
  (`!curFeed()`), the function sets `run = false` and removes the
  'on' class from `body`, but the UI might be left in an inconsistent
  state (e.g., the 'Start' button still shows, panels might be open).
  Recommendation: Ensure all UI state is properly cleaned up when
  starting fails.

4.6 KEYBOARD SHORTCUTS MISSING SHIFT CHECK
  Severity: LOW
  Location: `addEventListener('keydown', ...)` (index.html lines 714-719)
  Description: The keydown handler checks `e.target.tagName === 'INPUT' 
  || e.ctrlKey || e.metaKey` but doesn't check `e.shiftKey`. This means
  shift+number shortcuts might have unexpected behavior, though the
  current code doesn't implement shift-specific actions.
  Recommendation: Either add shift handling if needed, or explicitly
  check for shiftKey and ignore it.

4.7 syncMics PREMATURE CONTEXT CLOSE (index.html lines 524-531)
  Severity: MEDIUM
  Location: `syncMics()` function
  Description: The function closes the audio context if no mics are
  active:
  `if (ac && !mics.some(m => m.src)) { ac.close(); ac = an = mixer = null; }`
  This means if all microphones are closed, the audio context is
  destroyed, and subsequent microphone attempts will need to create a
  new context from scratch (requiring another user gesture).
  Recommendation: Consider keeping the context alive if there's a
  chance mics will be reopened soon, or add a specific "reset audio"
  action.

4.8 RENDER LOOP NULL VIDEO ELEMENT (index.html line 382)
  Severity: HIGH
  Location: `const f0 = curFeed(), m = ...`
  Description: If `curFeed()` returns a feed without a valid video
  element, or if the video element is removed/garbage collected, the
  `m` variable could be null, causing the entire render loop to exit
  (`if (!m) return;`). This could freeze the application until the
  feed is re-selected.
  Recommendation: Add null checks and recovery logic for the video
  element.

=============================================================
5. POSITIVE FINDINGS
=============================================================

5.1 24/24 TESTS PASS
  The project has 24 passing pytest tests, indicating good test
  coverage for the backend functionality.

5.2 WEBSOCKET PROTOCOL HANDLING
  The server correctly handles binary (JPEG frames) and text (JSON
  control messages) payloads over WebSocket, with proper classification
  of JPEG SOI markers vs Float32 PCM audio.

5.3 PER-CLIENT SESSION STATE
  Each WebSocket connection gets its own `_WebSocketSession` instance,
  preventing cross-client palette interference and centralizing
  cleanup on disconnect.

5.4 SSRF PROTECTION
  The camera proxy (`/camera_proxy`) validates URLs to prevent SSRF
  attacks, blocking loopback and private IP addresses.

5.5 RESPONSIVE DESIGN
  The CSS includes multiple media queries for different screen sizes
  (900px, 760px, 640px) and prefers-reduced-motion, showing good
  attention to responsive design.

5.6 WELL-STRUCTURED UI STATE MANAGEMENT
  The `App` object and `SEL`/`GAINS`/localStorage patterns provide
  decent state management for a web application of this complexity.

=============================================================
7. CONCLUSION
=============================================================
The Live Feed Quantizer application is functionally capable with a
well-designed WebSocket protocol and per-session state management.
However, several structural and functional issues need to be addressed
before the application is ready for broad deployment:

1. The render loop's video element check could cause the quantizer to
   silently stop processing frames.
2. The audio context initialization requires user gesture and might
   fail silently on some page loads.
3. The WebSocket URL construction has protocol detection edge cases.
4. The WebGL error handling replaces the entire page, providing poor
   user experience.

Overall score: 7/10 - Functional but requires fixes for robust deployment.
